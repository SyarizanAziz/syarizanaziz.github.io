Case study 01 · Adobe Workfront Fusion

Turning marketing requests into ready-to-run projects, automatically.

A set of Adobe Workfront Fusion scenarios that replaced daily manual project setup for a US enterprise marketing team. Every new request now becomes a project with the right brief form and task template attached.

The problem

The marketing team submits intake requests in Adobe Workfront for emails, webinars, digital ads, videos, web pages and more. Each request had to be converted into a project by hand, then given the right brief form and task template for its type.

Before

  • Repetitive conversion work every single day.
  • On busy days, requests with later due dates were pushed back so urgent ones could go first.
  • Stakeholders waited for their project to be set up.
  • Picking the wrong form or template meant rework later.

After

  • Requests convert into projects automatically as they come in.
  • The correct brief form and template are attached for each request type.
  • Project managers only review the project and adjust what is needed.
  • No request is missed. The team only steps in when an error is flagged.

What I built 5 scenarios

1

Auto Convert Requests to Projects

Live

The main flow. Converts each new request into a project, routes it down one of three paths by request queue, attaches the matching brief form and template, links the project back to the request and notifies the team.

2

Attach Additional Templates

Live

Lets a project manager add more work to a live project. They pick extra request types and set one field to Yes. Fusion appends the matching templates without touching the existing tasks.

3

Attach Activation Plan Templates

Live

When a project has an activation plan, Fusion loops through every selected channel (paid social, email nurture, events and more), attaches each template, and posts one combined update instead of many.

4

Sync Late Documents to Projects

Live

Files uploaded to a request after it became a project are copied into the project automatically, and the project owner is tagged with a link. No late assets get missed.

5

Request Routing and Assignment (v1)

Retired

The earlier version. It assigned people by request type and used a Data Store check so no request was processed twice. It was replaced by the conversion flow above, which handles the same job in one place.

Key decisions

Keep the mapping in a table, not inside the scenario

Each request type points to its brief form and task template in a Fusion Data Store. When the team adds a new request type or changes a template, they update one row. Nobody has to edit the scenario logic.

Fail safely instead of stopping

If a mapped template has been deleted, Fusion creates an issue on the project, assigns it to the project owner and tags the team with the template name. The rest of the run continues. Known harmless errors, like a form that is already attached, are ignored. Repeated unexpected failures still stop the scenario after maxErrors: 3.

Handle the exceptions in their own path

Website fixes, asset removals and translations each get their own path with a fixed template. A narrow override covers one request type from specific senders who need a different template. The common case stays simple.

Write it down for handover

I documented every scenario with its purpose, a module-by-module breakdown and its error handling, plus a mapping sheet and a flow diagram. The team can maintain it without me.
